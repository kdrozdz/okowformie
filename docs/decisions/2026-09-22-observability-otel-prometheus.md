# Observability: OpenTelemetry → Prometheus bez Collectora, tylko dev

- **Decyzja:** Metryki i błędy (backend Django + frontend Next.js) instrumentowane przez OpenTelemetry SDK, eksponowane bezpośrednio jako endpoint `/metrics` w formacie Prometheusa (port `9464` w obu serwisach) — **bez** pośredniczącego OTel Collectora. Prometheus scrape'uje oba serwisy bezpośrednio. Grafana jako warstwa wizualizacji nad Prometheusem, z jednym startowym dashboardem "HTTP overview" (request rate, error rate, latencja p50/p95), provisionowanym jako kod (nie klikanym ręcznie).
  Zakres: **tylko lokalny dev** (`docker-compose.yml`) — produkcja (Cyberfolks VPS) to osobna, przyszła decyzja.
  Błędy reprezentowane jako **metryki** (liczniki HTTP 5xx / wyjątków wg typu i endpointu), nie jako pełne logi/traces — bez Loki/Tempo na razie.
  Zestaw metryk: HTTP (request count, duration histogram) na obu serwisach + DB (Postgres) na backendzie. DB **nie** przez auto-instrumentację (`PsycopgInstrumentor` — patrz "Alternatywy", okazała się no-op), tylko przez własny middleware (`core.telemetry.DBQueryMetricsMiddleware`) owijający `connection.execute_wrapper` — histogram `django_db_query_duration_seconds`, etykieta `operation` (pierwsze słowo SQL). Cache (Redis) świadomie **poza zakresem** tego taska (`docs/todo/TODO.md`) — `RedisInstrumentor` odrzucony z tego samego powodu co `PsycopgInstrumentor`, a własny licznik dla Redisa nie był zlecony i nie ma dziś w kodzie miejsca analogicznego do `execute_wrapper` (wymagałby owijania klienta `redis-py` ręcznie).
- **Kontekst:** Task 14, zlecenie "logować metryki i błędy z OTel do Prometheusa, podstawowe metryki, ruch na stronie, błędy". Repo nie miało wcześniej żadnej warstwy observability (brak `LOGGING` configu w Django, brak `/infra`).
- **Alternatywy:**
  - **OTel Collector jako pośrednik** (apki → OTLP → Collector → Prometheus/inne backendy) — odrzucone na razie: dodatkowy kontener i warstwa bez realnej korzyści przy scope "tylko dev, podstawowe metryki" (YAGNI, `.claude/rules/engineering-principles.md`). Naturalna ścieżka rozbudowy, jeśli w przyszłości dojdzie tracing/logi do osobnych backendów (Tempo/Loki) — wtedy Collector odsprzęgnie apki od konkretnego backendu bez zmiany kodu instrumentacji.
  - **`django-prometheus`** (biblioteka prometheus_client bezpośrednio, bez OTel) — odrzucone: zadanie wprost wymagało warstwy OpenTelemetry, nie samego `prometheus_client`.
  - **`PsycopgInstrumentor`/`RedisInstrumentor` (auto-instrumentacja OTel dla DB/cache)** — początkowo w planie (sekcja 1 pierwotna), zainstalowane i `.instrument()`-owane bez błędu. Weryfikacja end-to-end (sekcja 5 planu taska) wykazała empirycznie: oba pakiety integrują się wyłącznie przez `TracerProvider` — nie skonfigurowany w tym tasku (decyzja: metryki, nie traces, patrz wyżej) — więc nie produkowały ani jednej serii metryk mimo realnego ruchu SQL/Redis w trakcie testu. Cichy no-op, bez błędu przy starcie ani przy instrumentacji — łatwy do przeoczenia bez ręcznej inspekcji `/metrics`. Zastąpione dla DB własnym middleware (`connection.execute_wrapper`, wzorzec analogiczny do licznika wyjątków w sekcji 2 planu); Redis zostaje poza zakresem.
  - **Liczenie unikalnych odwiedzających ("ile osób dziś weszło")** — świadomie **poza zakresem**. Prometheus/OTel liczy requesty, nie unikalnych użytkowników (etykietowanie po IP/sesji = eksplozja kardynalności, Prometheus się do tego nie nadaje z natury). To domena web analytics (Umami/Plausible/GA), inny problem i inne narzędzie — odłożone jako osobny, przyszły task, patrz `docs/todo/TODO.md`.
- **Znane ograniczenie do rewizji przy produkcji:** Python `PrometheusMetricReader` (OTel) nie stawia własnego serwera HTTP — wymaga `prometheus_client.start_http_server()` w procesie. Działa bezproblemowo przy `runserver` (jeden proces, dev). W produkcji gunicorn (`--workers 3`, `backend/Dockerfile`) odpaliłby 3 procesy próbujące zbindować ten sam port — kolizja. Nierozwiązane teraz (poza scope), zanotowane w `docs/todo/TODO.md` do podjęcia przy tasku deployu produkcyjnego.
- **Status:** aktywna.
